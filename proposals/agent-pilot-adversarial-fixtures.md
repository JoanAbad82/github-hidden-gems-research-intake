# Adversarial Fixtures for the Real-Data Model

## 1. Star Outside the Window

**Minimal pseudodata**

```json
{
  "window": ["2025-01-01T00:00:00Z", "2025-01-31T23:59:59Z"],
  "repository_id": 7001,
  "account_id": 42,
  "star": {
    "starred_at": "2025-02-01T00:00:00Z"
  },
  "issues_opened_in_window": [],
  "pull_requests_opened_in_window": []
}
```

**Exact assumption being attacked**

Any observed star proves endorsement or participation inside the bounded window, regardless of its timestamp.

**Expected verdict/state under the current model**

- Endorsement inside the window: **not established**
- Participation inside the window: **not established**
- The star remains positive evidence only for its actual timestamp.

**Incorrect verdict demonstrating a bug**

`endorsed_in_window = TRUE` or `participated_in_window = TRUE`

**Why this is not covered by the happy path**

A happy-path star occurs inside the requested interval. This fixture differs by one boundary-adjacent timestamp and detects implementations that discard temporal scope after finding positive evidence.

## 2. Same-Name Fork Is Not Lineage

**Minimal JSON**

```json
{
  "candidate": {
    "id": 8100,
    "full_name": "alice/widget",
    "fork": true,
    "parent": {
      "id": 9100,
      "full_name": "someone/widget"
    },
    "source": {
      "id": 9100,
      "full_name": "someone/widget"
    }
  },
  "target": {
    "id": 7001,
    "full_name": "upstream/widget"
  }
}
```

**Exact assumption being attacked**

A repository marked as a fork and sharing the targetâ€™s repository name must descend from that target.

**Expected verdict/state under the current model**

Fork lineage from `alice/widget` to repository ID `7001`: **FALSE**, because the available structural lineage points to repository ID `9100`, not the target.

**Incorrect verdict demonstrating a bug**

`fork_of_target = TRUE`

**Why this is not covered by the happy path**

The happy path has `parent`, `source`, or a parent-chain entry whose immutable repository ID matches the target. Here, names look compatible while the structural identifiers explicitly contradict the proposed lineage.

## 3. Login Reuse Does Not Establish Identity

**Minimal JSON**

```json
{
  "endorsement_actor": {
    "account_id": 42,
    "login": "octo"
  },
  "issue_actor": {
    "account_id": 84,
    "login": "octo"
  },
  "issue": {
    "repository_id": 7001,
    "created_at": "2025-01-15T12:00:00Z"
  },
  "window": ["2025-01-01T00:00:00Z", "2025-01-31T23:59:59Z"]
}
```

**Exact assumption being attacked**

Matching GitHub login text is sufficient to attribute participation evidence to the account that supplied endorsement evidence.

**Expected verdict/state under the current model**

Participation by numeric account ID `42`: **not established**. The issue establishes participation only for account ID `84`.

**Incorrect verdict demonstrating a bug**

`account_id_42_participated = TRUE`

**Why this is not covered by the happy path**

The happy path uses the same numeric account ID across evidence records. This fixture preserves an identical display login while changing the immutable identity key.

## 4. First Page Contains Only Documentation

**Minimal pseudodata**

```json
{
  "pull_request": 17,
  "changed_files_total": 2,
  "files_page_1": {
    "items": [
      {"filename": "README.md"}
    ],
    "has_next_page": true
  },
  "files_page_2": "not_fetched"
}
```

**Exact assumption being attacked**

If every changed path returned so far is explicitly non-code, `touches_code` may be set to `FALSE` before changed-file enumeration is complete.

**Expected verdict/state under the current model**

`touches_code = UNKNOWN`

**Incorrect verdict demonstrating a bug**

`touches_code = FALSE`

**Why this is not covered by the happy path**

The happy-path `FALSE` case completely enumerates all changed files and classifies every path as non-code. This fixture exposes premature classification caused by incomplete pagination.

## 5. Truncated Coverage Cannot Prove Absence

**Minimal pseudodata**

```json
{
  "repository_id": 7001,
  "account_id": 42,
  "window": ["2025-01-01T00:00:00Z", "2025-01-31T23:59:59Z"],
  "stars": {
    "enumeration": "complete",
    "matching_records": []
  },
  "forks": {
    "enumeration": "rate_limited_after_page_1",
    "matching_records_seen": []
  },
  "issues": {
    "enumeration": "complete",
    "matching_records": []
  },
  "pull_requests": {
    "enumeration": "deleted_or_inaccessible",
    "matching_records_seen": []
  }
}
```

**Exact assumption being attacked**

No matching record in the accessible subset is equivalent to complete bounded public-snapshot absence, even when a relevant participation channel is rate-limited, deleted, private, inaccessible, or truncated.

**Expected verdict/state under the current model**

Bounded public-snapshot absence of endorsement or participation: **UNKNOWN**

**Incorrect verdict demonstrating a bug**

`bounded_public_absence = TRUE`, `endorsed = FALSE`, or `participated = FALSE`

**Why this is not covered by the happy path**

The happy path has complete enumeration of every relevant public participation channel within the window. This fixture contains empty observed results but deliberately makes two required channels incomplete.
