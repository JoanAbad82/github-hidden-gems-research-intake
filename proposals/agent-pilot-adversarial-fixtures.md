# Adversarial Fixtures for the Real-Data Model

## 1. Star Outside the Window

**Minimal pseudodata**

```json
{
  "window": ["2025-01-01T00:00:00Z", "2025-01-31T23:59:59Z"],
  "repository_id": 7001,
  "account_id": 42,
  "star": {
    "starred_at": "2025-02-01T00:00:00Z"
  },
  "issues_opened_in_window": [],
  "pull_requests_opened_in_window": []
}
```

**Exact assumption being attacked**

Any observed star proves endorsement or participation inside the bounded window, regardless of its timestamp.

**Expected verdict/state under the current model**

- Endorsement inside the window: **not established**
- Participation inside the window: **not established**
- The star remains positive evidence only for its actual timestamp.

**Incorrect verdict demonstrating a bug**

`endorsed_in_window = TRUE` or `participated_in_window = TRUE`

**Why this is not covered by the happy path**

A happy-path star occurs inside the requested interval. This fixture differs by one boundary-adjacent timestamp and detects implementations that discard temporal scope after finding positive evidence.

## 2. Same Repository Name Does Not Prove Fork Lineage

```json
{
  "candidate": {
    "repository_id": 200,
    "name": "project",
    "parent_id": 150
  },
  "target": {
    "repository_id": 100,
    "name": "project"
  },
  "parent_chain": {
    "150": "UNRESOLVED"
  }
}
```

**Exact assumption being attacked:** Matching repository names can establish fork lineage, or an incomplete/mismatched structural chain can establish non-lineage.

**Expected verdict/state under current model:** `UNKNOWN`. The shared name must not produce `TRUE`, and the unresolved parent chain provides no complete, independently sufficient structural contradiction for `FALSE`.

**Incorrect verdict demonstrating a bug:** `TRUE` would prove name-based lineage leakage. `FALSE` would also be incorrect because the fixture does not contain a complete structural contradiction.

**Why this is not covered by the happy path:** The happy path has a fully resolved immutable-ID chain. This fixture tests ambiguity when names match but structural lineage cannot be completed.

## 3. Login-Based Commit Discovery Must Not Create Bounded Absence

```json
{
  "target_account": {
    "numeric_id": 42,
    "current_login": "new-login",
    "historical_login": "old-login"
  },
  "commit": {
    "sha": "abc123",
    "github_author_numeric_id": 42,
    "discovered_by_LIST_COMMITS_author_new_login": false
  },
  "discovery_completeness_proven": false
}
```

**Exact assumption being attacked:** `LIST_COMMITS author=current_login` discovers every commit attributed by GitHub to the target numeric account ID, despite login changes or reuse.

**Expected verdict/state under current model:** `UNKNOWN` for bounded participation absence. Numeric ID `42` remains the identity key, but the login-filtered discovery channel is not demonstrably complete.

**Incorrect verdict demonstrating a bug:** `BOUNDED_PUBLIC_ABSENCE` or `FALSE`.

**Why this is not covered by the happy path:** The happy path assumes login-filtered discovery returns the relevant commits before numeric-ID filtering. This fixture tests a false negative caused by that discovery optimization.

## 4. First Page Contains Only Documentation

**Minimal pseudodata**

```json
{
  "pull_request": 17,
  "changed_files_total": 2,
  "files_page_1": {
    "items": [
      {"filename": "README.md"}
    ],
    "has_next_page": true
  },
  "files_page_2": "not_fetched"
}
```

**Exact assumption being attacked**

If every changed path returned so far is explicitly non-code, `touches_code` may be set to `FALSE` before changed-file enumeration is complete.

**Expected verdict/state under the current model**

`touches_code = UNKNOWN`

**Incorrect verdict demonstrating a bug**

`touches_code = FALSE`

**Why this is not covered by the happy path**

The happy-path `FALSE` case completely enumerates all changed files and classifies every path as non-code. This fixture exposes premature classification caused by incomplete pagination.

## 5. Truncated Coverage Cannot Prove Absence

**Minimal pseudodata**

```json
{
  "repository_id": 7001,
  "account_id": 42,
  "window": ["2025-01-01T00:00:00Z", "2025-01-31T23:59:59Z"],
  "stars": {
    "enumeration": "complete",
    "matching_records": []
  },
  "forks": {
    "enumeration": "rate_limited_after_page_1",
    "matching_records_seen": []
  },
  "issues": {
    "enumeration": "complete",
    "matching_records": []
  },
  "pull_requests": {
    "enumeration": "deleted_or_inaccessible",
    "matching_records_seen": []
  }
}
```

**Exact assumption being attacked**

No matching record in the accessible subset is equivalent to complete bounded public-snapshot absence, even when a relevant participation channel is rate-limited, deleted, private, inaccessible, or truncated.

**Expected verdict/state under the current model**

Bounded public-snapshot absence of endorsement or participation: **UNKNOWN**

**Incorrect verdict demonstrating a bug**

`bounded_public_absence = TRUE`, `endorsed = FALSE`, or `participated = FALSE`

**Why this is not covered by the happy path**

The happy path has complete enumeration of every relevant public participation channel within the window. This fixture contains empty observed results but deliberately makes two required channels incomplete.
